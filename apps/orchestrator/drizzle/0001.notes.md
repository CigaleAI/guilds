# Drizzle `0001` baseline

`0001_baseline.sql` is a schema-only snapshot of core's DDL. A new
install applies it, then the later numbered files. Drizzle applies it
as custom SQL. `drizzle-kit generate` and `drizzle-kit push` play no
part in it.

## Properties

1. **No migration-metadata tables besides `__drizzle_migrations`.**
   Scripts live in `artifacts` (`kind` `script`). Collections live in
   `artifact_collections` and `artifacts`.
2. **No data.** Catalog rows and native-tool bindings come from
   `src/db/seed/`.
3. **`__drizzle_migrations` is left out of the snapshot.** Migrate
   creates it in schema `public`. Compare dumps after stripping it.
4. **`artifacts.search_document`** indexes the text of `note` and
   `memory` rows, and the search text of `object` rows. The standing
   task lives on `agents.task`.
5. **Session settings are not schema.** The snapshot keeps
   `default_tablespace` and `default_table_access_method` the way
   `pg_dump` emits them, and drops every other `SET` line.

## Regenerating it

`pnpm --filter @guildsrun/orchestrator exec tsx scripts/dump-baseline-schema.ts`
regenerates the file. It needs a PostgreSQL 17 server: the one at
`R1_ADMIN_DATABASE_URL`, or `127.0.0.1:5432` (the development stack's).
The script:

1. creates an empty, uniquely named database
2. applies **every** committed migration to it, `0001` and all later
   files
3. dumps it with `pg_dump --schema-only --no-owner --no-privileges`,
   run in a `postgres:17` container
4. drops `__drizzle_migrations` and the `drizzle` schema, strips the
   session settings, and adds statement breakpoints
5. overwrites `0001_baseline.sql`, then drops the database

The result holds the schema of every later migration too. While
later numbered files exist, a regenerated `0001` overlaps them.

The optional `test/integration/schema-diff.test.ts` compares a boot
migration against applying the numbered SQL files directly.
